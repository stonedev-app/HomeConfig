# worklog

ユーザーの作業ログ(org-mode)に、今のセッションで行った作業を要約して追記するスキル。明示的に頼まれたときだけ動く — セッションが終わりそうだからといって自動的に書き込みに行かない。

## 手順の全体像

1. 設定を読み込む
2. 対象ファイルを決める
3. 会話から今日の作業をdraftとして要約する
4. ファイル末尾を見て、今日の日付見出しが既にあるか判定する
5. 追記する
6. 追記結果を会話に提示する

以下、各ステップの詳細。

## 1. 設定を読み込む

このスキルのディレクトリ(SKILL.md と同じ場所)にある `config.md` を読む。書式は `config.example.md` と同じで、次の2項目を持つ。

- `dir`: ログファイルを置くディレクトリ。`~` はホームディレクトリに展開して扱う
- `filename`: ファイル名パターン。`{YYYY}`(西暦4桁)と `{MM}`(月2桁)をプレースホルダとして使える
  - 例: `worklog-{YYYY}.org`(年ごと)、`worklog-{YYYY}-{MM}.org`(月ごと)、`worklog.org`(単一ファイル)

`config.md` が無い場合は初回セットアップとして、ユーザーに保存先ディレクトリとファイル名パターンを尋ねる。既定値として `dir: ~/worklog`、`filename: worklog-{YYYY}.org` を提案し、そのままでよければそれを使う。回答をもとに `config.example.md` と同じ書式で `config.md` を作成してから、ステップ2へ進む。設定は人によって違うため、推測で勝手に決めずに一度だけ確認する。

## 2. 対象ファイルを決める

年月をハードコードせず、必ずコマンドで取得する。

```bash
date +"%Y %m"
```

`filename` の `{YYYY}` `{MM}` をこの値で置き換え、`dir` と結合したものが対象ファイルになる。ディレクトリやファイルが存在しなければ新規作成してよい。新規作成時も `#+TITLE` のようなプリアンブルは付けず、いきなり `* <date 曜>` から書き始める。

## 3. draftの作り方

ユーザーに「今日何やったか教えて」と聞き直さない。今のセッションの会話履歴だけから要約する。

- 1トピック = 1つの `**` 見出し。1セッションで複数の話題を扱っていれば `**` を複数作ってよい
- レベル3見出しは固定セットではなく、内容に応じて選ぶ: `*** 背景` `*** メモ` `*** 方針` `*** 手順概要` `*** 試してみたこと` など。使わないものは無理に埋めず省略する
- 背景/メモと手順概要など、セクション間で同じ情報を重複させない(書いた内容がどのセクションの役割かを意識する)
- `*** 手順概要` は完了した手順だけを淡々と書く。「Xを試した→エラーになった→原因はYだった→Zして解消した」という経緯・トラブルシューティングの物語にしない。試行錯誤があった作業でも、結果として何が必要だったか・何をすればよいかだけを言い切る形に要約する
  - 悪い例: 「docker-composeが動かなかった。ログを見たら原因はconfig.jsonの壊れたJSONだった。直したら解消した」
  - 良い例: 「Homebrew版はプラグインを標準パス外に置くため、~/.docker/config.jsonにcliPluginsExtraDirsを追加する必要がある」
  - 経緯そのものを記録として残したい、とユーザーが明示的に望んだ場合のみ `*** つまずいた点` のような専用セクションを立てる。デフォルトでは立てない

## 4. 今日の日付見出しの有無を判定する

worklogは常に時系列で末尾に追記されていくだけなので、「今日の日付見出しが存在するなら、それは必ずファイル中最後の `* <` 見出しである」という前提が成り立つ。中間への挿入は発生しない。

```bash
grep -n '^\* <' <file> | tail -1
```

この行から日付(`YYYY-MM-DD`)を取り出し、今日の日付と比較する。

- **一致**する → 同じ `* <date>` 見出しの配下(ファイル末尾)に `**` ブロックを追記するだけでよい
- **不一致**、または見出しが1つも無い(ファイル新規作成含む) → 新しい `* <today 曜>` 見出しごとファイル末尾に追記する

### 曜日を漢字1文字にする

暗算しない。曜日ズレのバグを起こしやすいので、必ずコマンドの結果を使う。

```bash
date +"%Y-%m-%d %u"
```

`%u` は ISO 準拠で 1=月 〜 7=日。対応表:

| %u | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|----|---|---|---|---|---|---|---|
| 曜日 | 月 | 火 | 水 | 木 | 金 | 土 | 日 |

## 5. 書き込み方法

常にファイル末尾への追記なので、Edit toolで「ファイルの既存最終行」を `old_string` のアンカーにして、その直後に新しい内容を続ける形にする(EOF追記は一意なアンカーが取りやすく安全)。対象ファイルがまだ存在しない場合(初回や、年・月が変わったとき)のみ Write tool で新規作成する。

書き込み前にユーザーへ確認は取らない。直接追記してから、追記した内容をそのまま会話に貼って見せる(ステップ6)。ログを git 管理している場合は `git diff` / `git checkout` で戻せる、と軽く触れる程度でよい。

## フォーマット規約

- 箇条書きは `-`。2スペース単位でネストする。継続行やURLは親項目のテキスト列に揃えてインデントする
- すべての見出し(`*` `**` `***`)の前に空行を1行入れる
- キーバインドなど「操作名: 値」を書くときは `- ファイルを開く/保存: C-x C-f / C-x C-s` のような形式

具体例(1トピック分のミニサンプル):

```org
* <2026-09-16 水>

** worklogスキルの作成

*** 背景

Claude Codeとの会話内容を作業ログに自動で書き込んでくれるスキルが欲しかった。

*** 方針

skill-creatorのガイドに沿って worklog スキルを新規作成する方針にした。
- トリガー: /worklog コマンド + 自然言語の依頼
- 書き込み: 確認を挟まず直接追記してから内容を見せる
```

## トーンガイド

磨き込みすぎない。作業ログは続けられることが一番大事で、完成度は二の次でよい。draftの言葉選びは「良い感じでまとまっていればOK」くらいの温度感にとどめ、何度も推敲を重ねたり改善提案を並べたりしない(提案するなら1〜2個まで)。

## 6. 書き込み後にすること

追記したブロックをそのまま会話に貼って見せる。ユーザーがその場で言葉や構成の修正を頼めるようにする。
